# 两套执行顺序机制：`rt_controller_list` vs 从接口边计算

日期：2026-10-03　分支：`humble-work`　对象：`feature/two-phase-manager` 的两趟调度
与 `humble-work` 的 `StagedExecutionGroup`

> 用户的问题：(1) 双向调度直接用 `rt_controller_list` 的顺序，这套顺序能确保执行顺序不出错吗？
> (2) `humble-work` 还有一套"根据 controller 接口判断顺序"的方式，两种调度方式哪个更好？
>
> **回答**：(1) **不能**，而且代码里有可复现的反例；(2) **两者是同一个算法**，差别只在
> **线性化从哪来**——所以正确的问法不是"哪个更好"，而是"**把哪个环节换掉**"。
> 结论见 §0 与 §6。

---

## 0. 结论速览

| 问题 | 结论 |
|---|---|
| 列表顺序能保证正确吗？ | **不能**。上游 `controller_sorting()` 有一条分支会把"没有命令接口的 chainable 子节点"排到**父之前**（§1），且顺序只在 `configure_controller` 里算（`add_controller` 不算） |
| 那两趟调度为什么还是对的？ | 因为它**校验**顺序，不满足就**拒绝整个模式**（`unschedulable_order`）。它是"**信任 + 校验**"，不是"保证" |
| 两套机制是不同算法吗？ | **不是**。两者都是"**一份线性化、两个相反遍历**"（§2）。staged 内核的注释自己就是这么写的 |
| 那差别在哪？ | **线性化的来源**：两趟从管理器列表拿；staged 从**边**自己算（`plan_.postorder`）。其次是拓扑要求与额外语义（§3） |
| 哪个更好？ | **没有支配关系**：staged 在顺序鲁棒性与语义上更强，两趟在采用成本与拓扑通用性上更强（§3） |
| 建议 | 保留两趟的 **YAML 前门**，但把**顺序改成从边计算**（§6）。这样既拿到 staged 的鲁棒性，又**不碰** `controller_sorting()` |

---

## 1. 列表顺序不能保证：证据

`ControllerManager::controller_sorting()`（`controller_manager.cpp:4088+`）的第一个分支：

```cpp
const std::vector<std::string> cmd_itfs = ctrl_a.c->command_interface_configuration().names;
if (cmd_itfs.empty() || !ctrl_a.c->is_chainable()) {
  if (ctrl_b.c->command_interface_configuration().names.empty() || !ctrl_b.c->is_chainable()) {
    return false;            // 两者都没有命令接口：保持原序
  } else {
    return true;             // <-- 没有命令接口的一方排前面
  }
}
```

于是：**一个"声明了 reference 接口、但不认领任何命令接口"的 chainable 子节点，会被排到它的父之前。**
父要读子导出的参考接口 → 这条边在列表里是**反向**的 → 两个遍历都会把它走错方向，
而**每周期调用次数依然完全正确**（这正是这个缺陷危险的地方：静默）。

**这不是推断，是可复现的**：`feature/two-phase-manager` 的
`an_order_that_inverts_an_edge_is_refused` 先断言管理器给出的顺序确实是 `[tp_leaf, tp_root]`
（子在父前），再断言启用两趟会被拒绝并给出"ordered AFTER its child"的理由。

另外两个容易忽略的点：

| 事实 | 代码位置 | 含义 |
|---|---|---|
| 只在 `configure_controller` 里 `stable_sort` | `humble-work` `controller_manager.cpp:991`（feature 分支为 `:946`；`add_controller_impl` 里**没有** sort，已核对） | `add_controller` **不排序**；最终顺序与**加载/配置顺序**有关，不是纯拓扑量 |
| 顺序由**字符串前缀**推断 | `get_following_controller_names` / `get_preceding_controller_names` | 依赖"接口名以 `<owner>/` 开头"这一约定，**声明为 `ALL` 的控制器**在排序眼里长得像"没有接口" |

**所以：列表顺序只能当作"一个候选线性化"，必须被校验。** 两趟调度当前正是这么做的
（`unschedulable_order`：任一条边的父下标 ≥ 子下标 → 拒绝整个模式，两端都点名）。

补充：列表**不是**执行代的一部分（成员集与模式是），所以每次列表变化都必须重建成员集。
`feature/two-phase-manager` 里四条会改列表的路径（`add_controller_impl`、
`configure_controller`、`unload_controller`、`switch_controller`）**都调用了**
`rebuild_two_phase_entries()`——这是"校验过的顺序 == 实际执行的顺序"能成立的前提，
值得在评审时单独盯住。

## 2. 两者是同一个算法

| | 两趟调度（管理器模式） | staged 内核 |
|---|---|---|
| 线性化 | `rt_controller_list`（上游排序） | `plan_.postorder`（**从边算出来**） |
| 状态趟 | 列表**反向**遍历 | postorder **正向**遍历 |
| 命令趟 | 列表**正向**遍历 | 同一个 postorder **反向**遍历 |
| 为什么成立 | 后序的反转是合法拓扑序 | 同上 |

`staged_execution_group.hpp:70` 的注释就是这么写的：
`update stage : postorder, iterated FORWARD (children before parents)`，命令阶段
`:330` 用同一个 `plan_.postorder` 倒着走。两者是**同一个构造**，只是顺序的来源不同。

**这一点很重要**：它意味着两者之间**不存在"原理上的优劣"**，可以逐环节替换，
而不必整体换实现。

## 3. 逐维对比

| 维度 | 两趟（信任 + 校验） | staged（自己算顺序） | 谁更强 |
|---|---|---|---|
| 顺序来源 | 管理器列表（上游 `controller_sorting()`） | 从边计算 `plan_.postorder` | **staged** |
| 对上游排序怪癖 | **不免疫**：会拒绝该配置 | 免疫 | **staged** |
| 顺序错的后果 | 拒绝整个模式（**不会静默跑错**） | 不适用 | 平（都安全） |
| **拓扑要求** | **只需存在一个合法拓扑序**；支持**多根**、支持**扇入**（两个父认领同一个子的不同端口） | `build_controller_hierarchy` 要求**单根、无环、无不可达**；且 `hierarchy.hpp:44-52` 明确要求"一个节点作为子**只能有一个父**"——**扇入被拒绝** | **两趟**（更通用） |
| 边冲突检查 | 无"一个端口两个写者"的显式检查（顺序校验碰巧会拒掉多数） | 显式：同一**端口**两个写者 → 抛异常 | staged |
| 每周期调用的额外保证 | 无（每阶段每成员一次；失败则本周期不跑命令阶段） | **帧语义 + 整组提交 + max_age** | **staged** |
| 采用成本 | **YAML 一行** | 需 C++ `set_staged_execution_group()`（**尚无 ROS 入口**，见 `PENDING_WORK` §2.2） | **两趟** |
| 与上游耦合 | 依赖列表顺序 + 每条边的下标比较 | 不依赖列表顺序，只依赖**成员集合** | staged |
| 实时路径开销 | 每个成员一次**指针二分查找**（`two_phase_index`） | 直接按 plan 数组索引 | 略偏 staged |
| 编译期能力 | `static_two_phase_admission` 描述层 + plan 等价性校验 | binding 直接产出 plan（`to_library_spec`） | 平 |

**结论：没有支配关系。** staged 在"顺序鲁棒性 + 语义强度"上更强；
两趟在"采用成本 + 拓扑通用性"上更强。而**它们最强的两项恰好互补**——
这是 §6 建议的出发点。

## 4. 一个容易被忽略的观察：staged 的"森林"限制比必要更严

`hierarchy.hpp` 的规则是"**一个节点作为子只能有一个父**"，理由是把它当作树来构建。
但两趟调度的数学要求只是**存在一个线性化**：对每条边 `父 < 子`。
扇入（两个父各自认领同一个子的不同端口）**不违反**这个条件，也不违反"一个端口一个写者"，
staged 却会抛异常拒绝它。

也就是说：**staged 在"顺序"这一维更强，但在"接受哪些拓扑"这一维更窄。**
如果目标是"尽量少拒绝合法配置"，两趟的姿态更合适；如果目标是"语义尽量强"，staged 更合适。

（这也是一个可以在论文里讲清楚的对比点：**同一调度构造，两种拓扑模型**。）

## 5. 两趟当前的真实弱点，收敛成一句话

> 两趟调度的**算法**没问题，**边推断**也没问题（和 staged 用的是同一类前缀推理）；
> 它唯一的弱点是**线性化的来源**——借用了上游的排序启发式，因此**必须**拒绝那些
> 启发式排不对、但**其实可以调度**的配置。

具体就是 §1 那个反例：一个"只导出参考、不认领命令接口"的子节点，
它的配置**是可调度的**（只要把它排在父之后），但两趟会拒绝。这是**能力性损失**，不是正确性问题。

---

## 6. 建议：保留 YAML 前门，把"顺序来源"换掉

**做法**：两趟调度不再遍历 `rt_controller_list`，而是：
1. 在**配置期**（非实时）用与 §1 相同的前缀规则推断出边集合——这段代码已经有了
   （`two_phase_rejections` 里的 owner 推断）；
2. 对边集合做**拓扑排序**，得到一条线性化 `order`（等价于 staged 的 `plan_.postorder`）；
3. 成员集与 `order` 一起发布进执行代（和现在发布 `two_phase_entries` / `two_phase_buckets` 一样）；
4. 实时路径**遍历 `order`**：反向跑 `update_phase`，正向跑 `handle_phase`。

**得到什么**：

| 变化 | 结果 |
|---|---|
| `unschedulable_order` 拒绝码 | **消失**——不再依赖上游排序，也就没有"排错了"这回事 |
| "只导出参考、不认领命令接口"的配置 | 从**被拒绝**变为**可调度**（能力性缺口补上） |
| 扇入（多父） | 继续可用（比 staged 的森林限制更宽） |
| 真正的环（A 认领 B 的、B 认领 A 的） | 需要**新的**拒绝码 `cyclic_dependencies`——这种配置在"两向同周期"语义下**确实无解**，拒绝是对的 |
| `controller_sorting()` | **完全不碰**（这是用户明确要求的） |
| 实时路径 | 少一次指针二分查找（直接索引 plan） |
| 发布协议 | `order` 与成员集同一个 generation（沿用现有做法） |

**代价**：一个配置期的拓扑排序（~40 行）+ 把实时路径的遍历从"列表 + 查表"改成"遍历 plan"。
回归面集中在两趟路径自身，不扩散到未启用该功能的配置。

**风险与待决问题**（实施前需要拍板，见 §7）。

## 7. 实施前需要拍板的问题（不建议现在动手）

1. **边推断用哪一套**？两趟现在用 `claimed_command_interfaces`（ACTIVE 用快照、INACTIVE 用声明）。
   staged 用调用方传入的 `command_interfaces`。两者在"声明 `ALL` 的控制器"上可能不同
   （快照 vs 声明的差异，审计里已有 F9 类讨论）。要统一，否则两套顺序可能不一致。
2. **环怎么处理**？直接拒绝，还是像跨速率桶那样给一个"有界滞后"的接纳（那就变成 P0-2 的推广）？
   我倾向**先拒绝**，并明确写"环在两向 0 滞后语义下无解"。
3. **顺序变化的时机**：`order` 必须和成员集同代发布；这要求所有改列表/改边的路径都重建它
   （现在四条路径已经重建成员集，新增一个 `order` 是同一处改动）。
4. **要不要顺手补"一个端口一个写者"的显式检查**？staged 有、两趟没有。
   加了它会**多拒绝**一些当前勉强能跑的配置，但那是正确的；需要决定是否算破坏兼容。
5. **和 staged 的关系**：这套改完之后，两趟与 staged 的**顺序部分**就等价了，
   差别只剩"前门（YAML vs C++）"与"额外语义（帧/整组提交）"。
   届时可以明确写：**两趟 = staged 的调度，去掉帧与整组提交**。

---

## 8. 不建议做的

| 不建议 | 理由 |
|---|---|
| 替换 `controller_sorting()` | 对所有配置生效的全局行为变更；而两趟**不需要**它正确，只需要**不依赖**它（§6 正是"不依赖"） |
| 为了顺序正确性直接把两趟换成 staged 内核 | 会把 YAML 一行采用变成 C++ API 采用，且丢掉扇入支持；收益（顺序）可以用 §6 更小的改动拿到 |
| 让两趟也要求"单根森林" | 比必要更严，会拒绝本来可调度的配置（§4） |

---

## 9. 一页话总结（可直接进论文）

> 两趟调度与 staged 内核是**同一个**调度构造（一份线性化、两个相反遍历），
> 它们的差别在**线性化的来源**：前者借用管理器列表的顺序并**校验**，后者从边**计算**。
> 借用带来的代价不是正确性（校验保证不会静默跑错），而是**能力**：凡是上游排序启发式排不对、
> 但本身可调度的配置，都被拒绝。把线性化的来源从"列表"换成"从边计算"——
> 这是一个配置期改动，不触碰上游排序——即可消除该拒绝码、补上这一能力缺口，
> 同时保留 YAML 一行启用与对一般 DAG（含扇入）的支持。
