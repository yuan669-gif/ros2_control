# 为什么本方案不更快——正面回答负结果

日期：2026-09-22
关联：`doc/HIERARCHY_FAIR_COMPARISON.md`（耗时与分配实测）、`doc/WIRING_COST_ANALYSIS.md`（接线成本）、
`doc/SCHEDULING_PERFORMANCE_COST.md`（性能侧调查）

`HANDOFF_MANUAL.md` §6 P0 把本文列为"尚未写"。它存在的目的只有一个：
**把"我们的方案更慢"这个负结果正面解释清楚**，而不是绕开它。

---

## 1. 先摆事实：负结果清单

| 指标 | 结果 | 证据 |
|---|---|---|
| `update()` 中位耗时 | 阶段化执行组约为手写 composite 的 **2 倍** | `HIERARCHY_FAIR_COMPARISON.md` §5 |
| 与原生 chaining 比耗时 | 同一量级或略高 | 同上 |
| 省集成代码 | **不独有**：库宿主同样做到"加一个节点 = 一条配置" | `WIRING_COST_ANALYSIS.md` §5 |
| 轨迹跟踪误差 | **无收益**；低带宽回路比值 0.97–1.00 | `CONTROL_COST_OF_LAG.md` §1、`GAZEBO_CASE_STUDY.md` §4 |
| 实时路径分配 | 执行组自身 0 分配，但 `ControllerManager::update()` 整体仍分配（Humble 既有代码） | `HIERARCHY_FAIR_COMPARISON.md` §4 |

**这些都不应被隐藏。** 下面逐条解释为什么它们**不应该**被期待是正的。

## 2. 负结果一：CPU 时间更慢——因为测的不是同一个量

### 2.1 FineMote 主张的是**控制延迟**，不是 CPU 时间

FineMote 的两阶段（`Update()` 正向 / `Handle()` 反向）要解决的问题是
**信息新鲜度**：让父节点在同一周期内看到子节点刚算出的状态。
它的收益体现在**控制回路的相位滞后**上，不体现在 CPU 周期数上。

我们的对照测的是 `ControllerManager::update()` 的**墙钟耗时**。
这是两个不同的量：

| 量 | 谁主张 | 我们的实测 |
|---|---|---|
| 控制延迟（周期数 / 相位滞后） | FineMote / 本方案 | **两趟：0 周期；单趟：L = 深度**（`TWO_PASS_VS_SINGLE_PASS.md`） |
| CPU 时间（µs / 次 `update()`） | 无人主张 | 两趟约为手写 composite 的 2 倍 |

**所以"更慢"并不反驳"更少的控制延迟"**——它们可以同时成立，而且在我们这里同时成立。
用 CPU 时间去否定一个控制延迟主张，是**指标错配**，等价于用"发动机更重"去否定"油耗更低"。

### 2.2 为什么两趟必然更慢（结构性的，不是实现问题）

两趟执行每周期至少多付：

1. **一次额外列表遍历**（`rt_controller_list` 正向 + 反向）；
2. **每控制器一次额外虚调用**（`update_phase()` + `handle_phase()`，而不是一次 `update()`）；
3. **每控制器每阶段一次帧校验**（周期号、采样年龄、有限性）。

而手写 composite 是**一个插件、一次 `update()` 调用**，内部两阶段是内联的标量代码，
连虚调用都被编译器消掉了。**在"每周期额外做 3 次虚调用 + 校验"这件事上，
两趟方案没有可能赢过内联的手写实现。**

公平的说法是：

> 阶段化执行组把"两阶段调度 + 校验 + 整组提交"做成**可复用的库**，
> 代价是每周期约 2 倍的 `update()` 耗时；
> 手写 composite 在**单一固定拓扑**上更快，但换拓扑要重写调度。

这正是 `WIRING_COST_ANALYSIS.md` §6 的结论，也与 `HANDOFF_MANUAL.md` §11
"不能声称更快"一致。

### 2.3 这个对照本身有多可信

| 限制 | 说明 |
|---|---|
| 非实时虚机 | 2 核 VM，`max` 波动 8–300 µs（调度噪声），**不能**当 deadline miss 统计 |
| 只报了 min/median/max | 未报 p95/p99，也未做 CPU 绑定 |
| 单一拓扑与算法 | 只测了三级链与两叶 fork |
| 未做消融 | 帧校验、整组提交各占多少耗时**尚未分离** |

⇒ 正确表述是"**在这条微基准上**中位耗时约为手写 composite 的 2 倍"，
而不是"本方案比手写 composite 慢 2 倍"。

## 3. 负结果二：跟踪误差无收益——两个独立原因

### 3.1 原因 A：低带宽回路本来就不敏感（这是定律，不是缺陷）

相位裕度损失 `ΔPM = 360·f_c·L·Δt` 与**穿越频率占控制频率的比例**成正比。

Gazebo 底盘外环 `f_c ≈ 0.5 Hz`、`Δt = 20 ms`（50 Hz）：

```text
ΔPM = 360 × 0.5 × 1 × 0.02 ≈ 3.6°
```

**一个周期只损失 3.6°**。在这样一个刻意放宽的外环上，**任何**测量都看不出 1 个周期的差别。
这不是机制无效，而是**该被控对象不在机制起作用的区间内**。
`SCHEDULING_PERFORMANCE_COST.md` §2 中同一控制器在 1 kHz 下的损失是 34.4°——差 10 倍，
因为绝对延迟 `L·Δt` 差 10 倍。

### 3.2 原因 B：能暴露效应的回路，其跟踪误差指标不敏感

这是本轮新增的实测结论，值得写进论文的方法学部分：

在 `SCHEDULING_PERFORMANCE_COST.md` §2 的高带宽被控例（1 kHz、`f_c` 接近 100 Hz）上，
我们尝试用**小信号跟踪误差 RMS** 作为指标，结果**无法区分**调度：

- 被控例是双积分器 + PD，**无积分作用** ⇒ 对**位置**参考的直流增益不为 1，
  稳态位置幅值远小于参考幅值，误差 RMS 被参考自身 RMS 主导（≈ `1/√2`），
  与滞后几乎无关；
- 加入积分作用后，环路阶数升高，边带裕度被积分项吃掉，
  误差 RMS 仍由参考主导。

**结论**：对"反馈用了陈旧状态"这类问题，

| 敏感指标 | 不敏感指标 |
|---|---|
| 相位裕度、可用增益上限、失稳点 | 小信号跟踪误差 RMS |
| 阶跃响应的初始滞后周期数 | 低频正弦的 RMS 误差 |

这与 `HANDOFF_MANUAL.md` §8 第 2 条完全一致，本轮**用实验再次确认**了它，
并且给出了一个更精确的说法：

> **能用跟踪误差看到收益的场景，与滞后造成危害的场景，不是同一个场景。**

滞后危害最大的地方是"带宽受限"的回路（`f_c` 接近 `1/Δt`）；
而带宽受限回路在**小信号**下本来就跟不上参考，误差由参考主导。
要看到收益必须用**大信号/阶跃/失稳边界**这类指标。

## 4. 负结果三：省集成代码不独有——这反而定位了正确的交付形态

`WIRING_COST_ANALYSIS.md` §5 用通用 composite 库证明：
"加一个节点 = 一条配置"**不需要修改 `ControllerManager`** 也能做到，
而且复用同一份内核。

因此"减少手写集成代码"**不足以**成为修改上游管理器的理由。
但两种宿主仍有真实差别（同文档 §6.3）：

| | manager 宿主 | 库宿主 |
|---|---|---|
| 节点可单独加载/激活 | 是 | 否（整树焊死在一个插件里） |
| 可与原生 chainable 控制器混用 | 是 | 否（只 claim 硬件接口） |
| 需要改动 `ControllerManager` | 是（薄适配） | 否 |

⇒ 交付形态应当是"**独立 header-only 库 + 可选薄适配**"，
这正是 `hierarchical_control/` 现在的形态。

## 5. 那么，本方案的价值在哪里（不含性能）

| 价值 | 性质 | 证据 |
|---|---|---|
| **单入口模型下双向同周期不可满足**（定理 1） | 不可能性结果 | `FORMAL_MODEL.md` + 穷举 6 种顺序 |
| 单趟滞后 = 深度（定理 2） | 定量下界 + 构造 | 内核 + 真实管理器 + Gazebo |
| 两趟充分、零额外存储（定理 3） | 充分性构造 | 内核 + 真实管理器 |
| 滞后 → 相位裕度损失 → 可用增益上限 | 代价定律 | `CONTROL_COST_OF_LAG.md` + `SCHEDULING_PERFORMANCE_COST.md` |
| 双向边在上游**静默降级**且**载荷顺序相关** | 上游行为 | `BIDIRECTIONAL_EDGE_ANALYSIS.md` |
| 整组提交不部分提交 | 可靠性契约 | 两叶 fork 故障实验 |
| 执行组运行路径零分配 | 实时性契约 | 100 次调用 0 分配 |

**这些都不是性能收益，也都不需要性能收益来成立。**

## 6. 论文里怎么写这三条负结果

建议放在单独一节 **"Costs and Negative Results"**，按以下口径：

1. **不更快**：明确报告 2 倍中位耗时，并说明这是"每周期多一次遍历 + 每控制器多一次虚调用"
   的结构性代价；同时指出测的是 CPU 时间，与 FineMote 主张的控制延迟不是同一个量。
2. **跟踪误差无收益**：明确报告，并给出**两个原因**（低带宽不敏感；能暴露效应的回路
   其 RMS 指标不敏感），把它作为**方法学贡献**而不是缺陷来写。
3. **省集成代码不独有**：明确报告，并说明它如何**否定**了扩展 `ControllerManager` 的必要性，
   从而把交付形态收敛到独立库。

再加一条**本轮新增**的诚实披露：

4. **一个被误读为收益证据的数值伪影**：`CONTROL_COST_OF_LAG.md` §8.2 的
   `1 : 0.502 : 0.311 : 0.225` 是显式 Euler 的 `Δt·kd = 2` 上限，不是控制上限；
   真实上限为 1570.8 / 785.3 / 523.5（比值 2.000 / 3.001），`L=0` 无上限。
   详见 `SCHEDULING_PERFORMANCE_COST.md`。

> 第 4 条写进论文会显得"自曝其短"，但它**提高**而不是降低可信度：
> 它证明我们的代价量化是经过积分格式核查的，而不是照搬仿真输出。
