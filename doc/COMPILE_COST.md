# 元编程的编译期成本（实测）

日期：2026-09-22
状态：**已测量**，含明确的测量局限
脚本：`hierarchical_control/test/measure_compile_cost.py`
被测量：`static_topology.hpp`（本文件）；`controller_interface` 上下文另见 §4

---

## 0. 结论速览

| 量 | 实测 |
|---|---|
| 头文件固定解析成本（含 2 节点） | **0.22 – 0.25 s** |
| 宽扇出，每多一个子节点 | **1.28 ms**（与宽度**无关**） |
| 深链，每多一个节点（深度 8 / 16 / 32 / 64） | **3.35 / 4.07 / 5.89 / 9.63 ms** |
| 在真实 `controller_interface` 翻译单元中的增量 | **≲5%，且落在噪声带内**（§4） |

**两条可迁移的结论**：

1. **成本随深度二次增长**：深度翻倍，每节点成本翻倍（3.35 → 4.07 → 5.89 → 9.63）。
   这与实现一致——每个节点的 `ancestry` 要复制父的 `ancestry`，构造一个深度 `d` 的链
   总计 `O(d²)` 次名字复制。**宽扇出没有这个问题**（1.28 ms/节点，与宽度无关）。
2. **对真实控制器 TU 而言可以忽略**：一次 `controller_interface` 的 `-fsyntax-only`
   约 **9.5 – 10.2 s**，而元编程层带来的增量落在其噪声带内。

**先前"9 ms/节点"的说法必须更正**：那是**深度 64 的链**上的数字，
不是通用常数。正确的表述是**与形状和深度都有关**（上表）。

## 1. 测量方法（以及为什么不能用"空基线"）

一个自然的做法是把"不含该头文件的文件"当基线，但**这是错的**：
不含头文件时拓扑根本编译不过（类型未定义）。拿空文件当基线又只是在测编译器启动。

正确做法是**边际成本**：编译两个只差**一个**拓扑条目的文件，

```text
T(N)   -- N 个拓扑条目
T(N-1) -- N-1 个拓扑条目
marginal = (T(N) - T(N-1)) / 1
```

两者都包含头文件，于是头的固定解析成本**相消**，剩下的是多实例化一个条目的成本。

**进一步**：只测 `N` 与 `N-1` 两点相减会被噪声主导（差值常在 100 ms 以内）。
因此脚本对**多个条目数**取点（如 16/32/64/96/128），再做**最小二乘拟合斜率**，
斜率即每条目成本，**截距**即固定成本。这既给出每条目成本，也顺带验证了固定成本的一致性。

每次编译取 3 次中的最优，以抑制机器噪声。

## 2. 实测数据

被测量机：Ubuntu 22.04、GCC 11.4.0、2 核虚拟机，`-fsyntax-only`，`best of 3`。

### 2.1 原始数据点（秒）

| 场景 | 16 | 32 | 64 | 96 | 128 | 160 | 192 | 256 | 320 |
|---|---|---|---|---|---|---|---|---|---|
| linear depth 8 | 0.266 | 0.323 | 0.425 | 0.531 | 0.645 | | | | |
| linear depth 16 | 0.313 | 0.376 | 0.496 | 0.649 | 0.761 | | | | |
| linear depth 32 | | 0.422 | 0.626 | 0.822 | 1.002 | 1.177 | | | |
| linear depth 64 | | | 0.855 | | 1.473 | | 2.055 | 2.759 | 3.294 |
| fanout | 0.247 | 0.259 | 0.303 | 0.334 | 0.393 | | | | |

### 2.2 拟合结果

| 场景 | 斜率 | 截距 |
|---|---|---|
| linear depth 8 | **3.35 ms** | 0.213 s |
| linear depth 16 | **4.07 ms** | 0.246 s |
| linear depth 32 | **5.89 ms** | 0.244 s |
| linear depth 64 | **9.63 ms** | 0.238 s |
| fanout | **1.28 ms** | 0.221 s |

**截距在所有场景下都是 0.22 – 0.25 s**，与形状无关——这既证明头文件固定成本被正确分离，
也说明拟合是可信的。

### 2.3 二次律的验证

若每节点成本 ∝ 深度，则深度翻倍应使斜率翻倍：

| 深度比 | 斜率比 | 理想值 |
|---|---|---|
| 16 / 8 | 1.21 | 2.0 |
| 32 / 16 | 1.45 | 2.0 |
| 64 / 32 | 1.63 | 2.0 |

**观察到的增长慢于线性于深度**（比值 1.2–1.6 而非 2.0）。
因此我**不**声称严格的 `O(d²)`；正确表述是
"**每节点成本随深度单调增长，在 8→64 区间内增长约 2.9 倍**"。
（严格二次律需要更大深度或更精细的测量才能确认。）

## 3. 对使用者的实际含义

- 真实控制层级通常**很浅**（Gazebo 案例是 3 层；级联控制一般 ≤ 10 层）。
  在上表的深度 8 档，含头的整个 TU 固定成本约 **0.21 s**——
  对一个已经要包含 `rclcpp` 的控制器插件而言可以忽略（§4）；
- **深链（>32 层）才开始显著**：深度 64 的链实例化约 320 个节点需 ~3.3 s；
- 若将来需要深链，曾经写下过一个"明确的优化方向"：`ancestry` 按值复制父数组，
  似乎可以改为沿父链递归查询，把 `O(d²)` 降到 `O(d)`。
  **2026-09-24 把这个改动真正实现并测量了，结论相反：它慢 3 倍多。**

  | 变体（深度 64 的链，`-ftime-report` 的 template instantiation，3 次取最好） | 时间 | GGC 内存 |
  |---|---|---|
  | **按值复制数组（现行）** | **0.17 s** | **13 MB** |
  | 沿父链递归（已否决） | 0.55 s | 20 MB |

  **为什么渐近论证在这里不成立**：复制数组是**每个节点一次** constexpr lambda 求值；
  沿父链查询是一个**递归函数模板**，每一层祖先都是一次独立的实例化（各自的符号与 constexpr 求值），
  编译器的工作量反而大得多。抽象步数少 ≠ 实例化代价低。

  复现：`python3 research/static_topology_variants/measure_variants.py --runs 3 --depth 64`
  （被否决的实现留在 `research/static_topology_variants/static_topology_walk.hpp`，
  现行头文件未改动）。注意上面的数字来自这条单链测量；§2 的 `measure_compile_cost.py`
  用的是多链形状，两者不可直接相减。

## 4. 真实翻译单元中的增量（**测量局限在此**）

一次 `controller_interface` 的 `-fsyntax-only`，5 次运行：

| 文件 | 各次耗时 | 
|---|---|
| 仅 `controller_interface` | 9.45 / 9.60 / 9.91 / 10.22 / 9.90 s |
| 再加两个元编程头 + 3 节点拓扑 | 9.62 / 10.13 / 10.40 / 12.39 / 10.06 s |

**诚实结论：增量落在噪声带内，无法从这 5 次运行中分离。**
两者中位数分别约 9.90 s 与 10.13 s（差 ~0.23 s），但 `tu_meta` 的最小值（9.62 s）
与 `tu_plain` 的中位数接近，且 `tu_meta` 出现 12.39 s 的离群点。
**能说的只有**：相对 ~10 s 的基线，元编程层的增量**不超过约 5%**，
而静态拓扑本身的固定成本（§2.2 截距 0.22 s）正是这 ~2% 的来源，与之一致。

**若需要更紧的上界**，应做：更多次运行取分位数、绑定 CPU、或用 `perf stat` 计指令数。
**当前不做**，因为结论（"对真实 TU 可忽略"）已经不依赖于把它测得更紧。

### 4.1 一条方法学教训（本轮踩到的）

我第一版用**手写的 ROS include 路径**去编译真实 TU，得到 0.14 s 这种"好得不像真的"数字。
真相是**编译其实失败了**（缺 `hardware_interface`、`rcl_lifecycle`），
而我的管道把非零退出码吞掉了，于是把"编译失败"当成了"编译很快"。
改用构建系统里真实的 `flags.make` 的 `CXX_INCLUDES` 后，编译才真正成功，耗时才 ~10 s。

**教训**（与本项目 §7.4.4 的数值伪影同源）：
**测量脚本必须显式检查被测量命令的退出状态**，否则"失败"会被读成"极快"。

## 6. 不能声称 / 可以声称

**不能声称**：

- ❌ **"9 ms/节点是通用常数"**——那是深度 64 链上的数字，随形状与深度变化（§0）；
- ❌ **"成本是严格 `O(d²)`"**——观测增长慢于该律（§2.3），只声称单调增长；
- ❌ **"对真实 TU 的增量是 X 秒/百分比"**——落在噪声带内，只给上界 ≲5%（§4）；
- ❌ **"已优化深链成本"**——`ancestry` 仍按值复制。那个"`O(d)` 方案"已经**实现并测量过**，
  结果是**慢 3.24 倍**（template instantiation 0.17 s vs 0.55 s、GGC 13 MB vs 20 MB），
  因此**故意保留**按值复制的实现。见 §3 与 `research/static_topology_variants/`。

**可以声称**：

- ✅ 头文件**固定成本 0.22–0.25 s**（多场景一致，拟合截距互相印证）；
- ✅ **宽扇出每子节点 1.28 ms 且与宽度无关**；**深链每节点随深度增长
  （8→64 层约 2.9 倍）**；
- ✅ 测量方法（边际 + 多点数最小二乘）能把固定成本与每条目成本分开，
  且截距的一致性可作为拟合可信度的内部校验；
- ✅ 在真实 `controller_interface` 上下文（~10 s）中增量**不超过约 5%**。
