## 摘要

`ros2_control` 的控制器模型是**单入口**的：每个控制器每个控制周期恰好被调用一次
`update()`。当两个控制器之间存在**双向耦合**——父控制器消费子控制器算出的状态（状态边），
同时子控制器消费父控制器产生的参考（参考边）——时，本文证明：**在同一周期内使两条边同时新鲜
是不可能的**。使状态边新鲜要求子先执行，使参考边新鲜要求父先执行，二者矛盾；
在单入口模型下，任何调度顺序都必然使至少一条边的信息陈旧至少一个周期，
且参考一致的单趟调度会使**每一条状态边**都陈旧。

我们把这一不可能性刻画为定理并给出构造性证明，用穷举全部执行顺序的实验加以验证；
进一步证明单趟调度的陈旧量**恰好等于级联深度 `D`**，并给出**上界与下界**。
随后给出修复方案：**一个线性顺序、两个相反方向的遍历**（状态阶段按后序正向，
命令阶段按同一顺序反向）。该方案充分、只需 `O(|V|)` 存储，且两趟复用**同一份**线性化，
**不需要为第二趟维护第二份拓扑顺序**，并可在配置期判定环形依赖。

更进一步，我们把"两趟"从**充分**升级为**最优**：定义**同周期要求图** `D`，
证明 **`k` 趟调度存在当且仅当 `D` 的边可划分为 `k` 个无环子集**
（定理 P1），并证明对**每一级都双向的级联**（**任意深度**）最少趟数**恰为 2**
（推论 P3）。也就是说两趟**不可改进**；而级联深度**不增加趟数**，
只增加单趟调度的滞后。

我们把"滞后一个周期"从周期数换算为控制量：`L` 个周期的滞后等价于纯传输延迟 `L·Δt`，
造成相位裕度损失 `ω_c·L·Δt`，进而给出闭环带宽上限 `f_c ≤ B/(2π·L·Δt)`；
在 `Δt = 1 ms`、30° 裕度预算下，深度 2 把带宽压到 42 Hz、深度 4 压到 21 Hz。
本文的闭环实验（**精确逐步更新**，并先校验该积分格式给出的上限与相位裕度定律吻合）在调度侧
验证了这条链。**相位裕度定律预测**的可用增益上限为 `L = 1, 2, 3` 时
**1570.8 / 785.3 / 523.5**（即下降比 **1 : 0.500 : 0.333**，**精确等于** `1/(L+1)`）；
**时间域实测**为 **1582.8 / 856.6 / 591.8**（下降比 **1 : 0.541 : 0.374**，
深度 1→2、1→3 的上限比为 **1.848 / 2.675**）。实测**系统性偏高 1%–13%**，
因为判据是**有限时域**（峰值有界）而非无穷时域稳定性边界；该差异我们**明确报告**。
两趟执行（`L = 0`）在实用范围内**没有上限**。

我们在三类真实系统上验证了契约：内核级穷举、**真实 `ControllerManager`**
（单趟根节点陈旧 2 个周期 = 深度；两趟全为 0）、以及**真实 Gazebo 物理仿真闭环**
（单趟 50 Hz 陈旧 1 周期 = 20 ms，20 Hz 陈旧 50 ms；两趟均为 0，2/2 复现）。
在**真实 Humble 代码**上进一步发现：双向对**总是**被排成"参考生产者在前"且与注册顺序无关
⇒ 状态边系统性陈旧；`configure_controller` 对该声明**完全不校验**，冲突完全静默。
对 Jazzy/master 的源码逐字节比对表明，排序实现已换成递归插入启发式，
双向边的结果转为**依赖加载顺序** ⇒ 同一拓扑从"确定"变为"不确定"，而仍然**没有诊断**。

本文**同时报告负结果**：本方案**不更快**（中位耗时约为手写复合控制器的 2 倍）、
**跟踪误差无收益**、**省集成代码并非其独有**。
我们还披露并修正了一个**曾被误读为收益证据的数值伪影**：
一份早期测量报告"可用增益预算每周期按 `1/(L+1)` 缩水"（比值 `1 : 0.502 : 0.311 : 0.225`，
"与理论吻合"），而该比值**精确等于显式 Euler 积分的稳定性上限 `Δt·kd = 2`**——
因为该格式中的有效阻尼恰为 `kd`，假上限天然按 `1/(L+1)` 缩放。
改用精确更新后，实测下降比是 **1 : 0.541 : 0.374**、定律预测是 **1 : 0.500 : 0.333**，
而伪影给出的是 **1 : 0.502 : 0.311**——三者形状相近，
**但只有后者的 `(L+1)` 形状来自积分格式而非控制回路**。这正是该伪影难以察觉的原因。

**关键词**：ROS 2 `ros2_control`；控制器级联；调度顺序；数据新鲜度；两阶段执行；
相位裕度；不可能性结果；可复现性

## 1. 引言

### 1.1 背景：级联控制里的"双向依赖"

级联控制是运动控制的常态，而**同一对控制器之间相互依赖两个方向**也是常态，不是特例。

**例 1（POV 底盘）**：常见结构是「底盘级 → 轮级」。底盘控制器把位姿误差变成两轮的速度参考
（父 → 子），轮控制器跟踪该参考并输出力矩；同时底盘还要用轮端估计的**行程**做航位推算
（子 → 父）。于是同一对父子之间：

- **参考边**：父产生参考，子消费（父 → 子）；
- **状态边**：子产生状态估计，父消费（子 → 父）。

**例 2（估计器 + 控制器级联）**：上游的典型用例是"估计器 → 控制器"的状态链，
即只有状态边。但一旦控制器还要把**自己产生的参考**回喂给估计器（例如用期望速度做前馈补偿），
两条边就同时出现。

**例 3（共享子模块）**：一个估计模块同时被两个控制器消费，其中一个控制器还向估计器提供参考。

`ros2_control` 用 **chainable controller** 表达这类层次：子控制器导出 reference interface，
父控制器在 `command_interface_configuration()` 中 claim 它，管理器据接口名推导依赖并排序。
此外，从 Jazzy 起控制器还可以导出 **state interface**，使"子产状态、父消费"也能通过接口表达。

**关键点在于**：上游分别实现了这两个方向的机制（reference chaining 与 state chaining），
但两者是为**单向**场景设计的。本文要回答的正是"**两者同时出现时会怎样**"。

### 1.2 问题

`ros2_control` 的控制器模型是**单入口**的：每个控制器每周期恰好被调用一次 `update()`，
在该次调用内既摄取输入、又产生输出。于是当同一对父子之间**两条边同时存在**时：

- 使**状态边**本周期新鲜，要求子控制器先执行；
- 使**参考边**本周期新鲜，要求父控制器先执行。

**两者在同一周期内不可能同时成立。** 这不是实现缺陷，而是模型的结构性后果：
只要每个控制器只有一个 `update()` 入口，就不存在一个执行顺序能同时满足两个相反的要求。

**为什么值得写成论文，而不是"提个 issue 修一下"。** 有三个理由：

1. **它不是可以绕过的工程细节。** 上游的排序机制**不会报错、不会告警、也不会检测**；
   在 Humble 上它**确定地**退化为"参考边新鲜、状态边陈旧一个周期"，
   在 Jazzy/master 上则**取决于控制器的加载顺序**（§4）。也就是说，
   同一个拓扑换一个加载顺序，行为就变了，而**没有任何诊断**。
2. **它的代价是定量的、并且只惩罚高带宽系统。** 一个周期的陈旧等于纯传输延迟 `Δt`，
   造成相位裕度损失 `ω_c·Δt`。低带宽外环几乎无损，而**恰好最需要同周期传播的高带宽级联会被打垮**
   （§6）。
3. ~~**修复它的方案有一个精确的最优性界限。**~~ **（2026-09-23 修正，见 §3.8）**
   本文证明了"一个线性顺序、两个相反方向的两趟执行"对任意深度的双向级联都够用（§3.5），
   并且"完整阶段遍历次数"不能再降。但后者对**任何**含环的要求图都成立（边的正/反向二分），
   所以它是**平凡分类**，不是树形结构的独立最优性发现。

**本文不主张的**：两阶段执行本身不是新机制（FineMote、Orocos 等已有）；
上游也没有"bug"（我们未发现任何规定禁止该组合）。本文主张的是
**不可能性刻画 + 代价量化 + 在真实系统上的验证**，以及一份诚实的负结果清单（§7.4）。
（"趟数最优性"已于 2026-09-23 降级为平凡分类，见 §3.8。）

### 1.5.2 两阶段调度与嵌入式框架

FineMote 的机制是"一个线性注册表，`Update()` 正向遍历、`Handle()` 反向遍历"，
即**同一顺序、两个方向**。实时框架（如 Orocos）与同步数据流模型中也有按阶段划分执行的做法。

**本文与它的关系**：机制本身**不是**本文的贡献。本文的贡献是把它证明为

### 1.5.3 调度中的不可能性与同步

"两个相反顺序要求不能同时满足"在并发与实时调度中并不陌生（例如优先序反转、
同步数据流中的一致性条件）。图着色/无环边覆盖类问题也是经典组合优化。

**本文与它的关系**：我们**不主张**发明这类不可能性或组合刻画。

最少趟数 = 要求图的无环边覆盖数，且双向级联恰为 2（§3.8）。
该刻画的双向证明是本文给出的。

### 1.5.5 级联控制中的相位裕度

"滞后 = 传输延迟，其代价是 `ω_c·τ` 的相位裕度损失"是经典结论，
在控制教材中属于标准材料。

**本文与它的关系**：我们**不主张**发明该定律。本文用它把"**调度滞后**"

## 2. 背景与上游现状

### 2.1 单入口控制器模型（本文的形式化前提）

`ControllerManager` 每周期依次执行 `read()`、`update()`、`write()`。`update()` 遍历已加载的
控制器列表，对每个激活控制器调用**一次** `update(time, period)`。

形式化地，本文所称的**单入口模型**指：

> **(SE)** 每个控制器在每个控制周期内恰好有一个**融合调用点**：该次调用中它既摄取输入
> （读子状态、读父参考），又产生输出（写自己的状态、写参考、写执行器命令）。

**为什么必须把它写成显式前提**：定理 1 的不可能性是 **(SE) 的推论**，不是 `ros2_control`
某个版本的实现缺陷。因此：

- 如果 (SE) 成立（Humble、Jazzy、master 均成立，见下），不可能性适用；
- 如果某个框架允许控制器暴露**两个**调用点（例如估计阶段与命令阶段分开），
  不可能性**不适用**——这正是本文的修复方案（§5）所做的：把 (SE) 换成两阶段契约。

**(SE) 的可证伪性**：这是一条关于实现的可检验断言。我们核对了两点：
`update()` 的循环体对每个控制器只调用一次（Humble 与 master 的
`controller_manager.cpp` 均如此），且控制器接口中没有第二个每周期入口。
若上游未来引入分离的摄取/产生入口，(SE) 失效，本文的不可能性结论也随之不再适用——
这是一个**可被推翻**的定位，而不是不可证伪的叙述。

### 2.2 上游已具备的能力（必须正面引用）

1. **state chaining**：估计器 → 控制器方向。Jazzy 起 `ChainableControllerInterface` 可导出
   state interface（`on_export_state_interfaces()` 等），使父控制器可以 claim 子控制器的状态。
   ⇒ 本文"Humble 无法导出 state 接口"**只对 Humble 成立**，属版本限制，**不是本文发现**。
2. **排序已考虑状态边**：issue #1123（2023-10-01 提出，2026-04-11 关闭）与更早的 commit
   `69b3225` 已把 `get_following_controller_names` / `get_preceding_controller_names` /
   `controller_sorting` 改为考虑 `state_interface_configuration().names`。
3. **lifecycle id 已缓存**：Jazzy 的 `ControllerInterfaceBase::get_lifecycle_id()` 文档明确写
   "cached internally to avoid calls to `get_lifecycle_state()` in the real-time control loop"。
   ⇒ 本文"`get_current_state()` 会在实时路径分配"**只对 Humble 成立**。

**这三条对本文的约束**：它们把若干可能被写成"发现"的点**降级为版本差异**。
我们选择把它们**前置声明**而不是留给审稿人指出，因为一篇以"不可能性"为主张的论文，
其可信度取决于**不夸大**任何相邻的观察。

### 2.3 反例防护：这是"未覆盖"，不是"被禁止"

我们检索了上游文档与 issue，**未发现**任何规定禁止"同一控制器对同时声明 reference 与 state 边"。
[issue #2189](https://github.com/ros-controls/ros2_control/issues/2189) 只澄清了
preceding/following 的术语（已关闭，属文档澄清）。

因此全文口径统一为：**该组合未被覆盖（uncovered）**。
**不写"上游禁止"，更不写"上游有 bug"**——后者需要 Jazzy/Rolling 数据通路复现，
而该复现**当前因环境限制未完成**（见 §9.2）。

## 3. 形式化模型与不可能性

### 3.1 模型

控制器集合 `V = {1..n}`。节点 `i` 在周期 `k` 具有内部状态 `x_i(k)`、输出 `u_i(k)`、
外部输入 `h_i(k)`。对父 `p` 与子 `c`：

- **参考边** `(p,c) ∈ R`：`u_p` 被 `c` 作为参考消费；
- **状态边** `(c,p) ∈ S`：`x_c` 被 `p` 消费。

两者**可以同时存在**于同一对 `(p,c)`——这正是级联控制（PDS、POV 底盘）的常态。

阶段函数：

```text
Update :  x_i(k) = f_i( x_i(k-1), { x_j(k) : (j,i) ∈ S }, h_i(k) )   // 摄取，改内部状态
Handle :  u_i(k) = g_i( x_i(k),   { u_p(k) : (p,i) ∈ R } )           // 由状态产生输出
```

约定：`Handle` 使用**本周期**的 `x_i(k)`，即同一节点的 `Update` 必须先于 `Handle`。

**调度**：

- **单趟**：一个全序 `π`；每周期按 `π` 顺序，每个节点执行一次**融合调用**
  （同一次调用内算 `x_i(k)` 与 `u_i(k)`），只能读到此前本周期已写入的值。
- **两趟**：一个全序 `L`；先用 `reverse(L)` 跑一遍 `Update`，再用 `L` 跑一遍 `Handle`。

**滞后** `λ ≥ 0`：消费者在本周期用生产者**本周期**的值时 `λ = 0`（新鲜）；
用 `m` 个周期前的值时 `λ = m`。

### 3.2 定理 1（单趟不可满足性）

> 若 `(p,c) ∈ R` 且 `(c,p) ∈ S`，则**任何单趟调度**都使这两条边中至少一条的滞后 `≥ 1`。

**证明.** 融合调用只读取"此前本周期已写入"的值。

- 使状态边新鲜（`p` 的 `Update` 读到 `x_c(k)`）要求 `c` 的融合调用先于 `p`：`pos(c) < pos(p)`；
- 使参考边新鲜（`c` 的 `Handle` 读到 `u_p(k)`）要求 `p` 的融合调用先于 `c`：`pos(p) < pos(c)`。

两式矛盾，故至少一条滞后 `≥ 1`。∎

**验证**：`every_single_pass_order_is_stale_in_some_direction`
穷举 3 节点链的**全部 6 种**执行顺序，断言每一种都至少有一个方向滞后 `> 0`。

### 3.3 推论 1（参考一致的单趟 ⇒ 状态边必陈旧）

> 设 `π` **尊重参考边**（对所有 `(p,c) ∈ R` 有 `pos(p) < pos(c)`）。则同时具有两条边的每一对，
> 其**状态边滞后 `≥ 1`**。

**证明.** 若状态边滞后为 0，则 `pos(c) < pos(p)`，与 `pos(p) < pos(c)` 矛盾。∎

**意义**：任何"正确"的管理器顺序都必须尊重参考边（否则子节点拿到陈旧参考，控制上更糟）。
因此**单趟 + 尊重参考边 ⇒ 状态方向必然陈旧**。这不是实现缺陷，而是结构性结论，
也正是第 4 章在真实 Humble 代码上观察到的现象。

### 3.4 定理 2（滞后 = 深度）

> 设 `n_0 … n_D` 是一条链，每级同时有参考边 `(n_i, n_{i+1}) ∈ R` 与状态边 `(n_{i+1}, n_i) ∈ S`。
> 若 `π` 尊重参考边，则叶节点 `n_D` 的信息到达根 `n_0` 的滞后**恰好为 `D`**。

**证明.**

- **下界**：由推论 1，每级状态边滞后 `≥ 1`，故每级至少增加一个周期：
  `x_{n_i}(k)` 依赖 `x_{n_{i+1}}` 在周期 `≤ k−1` 的值，归纳得依赖 `h_{n_D}` 在周期 `≤ k−(D−i)` 的值。
  取 `i = 0` 得滞后 `≥ D`。
- **上界**：取 `π = (n_0, …, n_D)`，归纳得 `x_{n_i}(k) = F(x_{n_{i+1}}(k−1))`，故滞后 `≤ D`。

两者合起来给出 `= D`。∎

**验证**：内核级阶跃响应测得 root 滞后 `2`、mid `1`、leaf `0`（`D = 2`），下行全 `0`；
**管理器级**在真实 `ControllerManager` 上复现同样的 `0/1/2`。

### 3.5 定理 3（两趟充分性）

构造统一方向图

```text
G = { (p,c) : (p,c) ∈ R } ∪ { (p,c) : (c,p) ∈ S }        // 统一为"父先于子"方向
```

若 `G` 无环，则存在全序 `L` 使 `G` 的每条边都满足 `pos_L(p) < pos_L(c)`。

> 两趟调度（`reverse(L)` 跑 `Update`，`L` 跑 `Handle`）使**每条边的滞后都为 0**。

**证明.**

- **状态方向**：对 `(c,p) ∈ S`，由 `G` 构造 `L` 中 `p` 在 `c` 之前，故 `reverse(L)` 中 `c` 在 `p` 之前，
  `p` 的 `Update` 读到 `x_c(k)`，滞后 0。
- **参考方向**：对 `(p,c) ∈ R`，`L` 中 `p` 在 `c` 之前，故 `c` 的 `Handle` 读到 `u_p(k)`，滞后 0。
- 整个 `Update` 趟先于整个 `Handle` 趟完成，故 `g_i` 总看到本周期状态。∎

**存储**：只有**一个**顺序 `L`，两个方向由正向/反向遍历得到 ⇒ `O(|V|)`，
与 FineMote 的线性注册表一致；**不需要为第二趟维护第二份拓扑数组**。
内核的其余存储（`preorder`/`postorder` 两份线性化，以及按节点与端口大小分配的
scratch、frame、committed 缓冲）仍是 `O(|V|)`，两趟相对单趟不改变量级。

**关键洞察**：**后序（postorder）的反转天然是"父先于后代"的合法顺序**
（后序保证每个后代排在其祖先之前）。因此**一份线性化同时满足两个方向**，
不需要为命令阶段单独维护拓扑数组。实现中 `L = reverse(plan_.postorder)`：
状态阶段走 `postorder` 正向，命令阶段走 `postorder` 反向。

### 3.6 推论 2（`G` 无环是充分条件，**不是**必要条件）

> **修正（2026-09-23，外部评审 R2）**：本节早期版本称"若 `G` 含环则任何调度都不可能"，
> **该命题已撤回**。反例：reference 边 `A→B` 与状态边 `A→B` 会让 `G` 出现 `A↔B`，
> 但实际阶段约束 `S_A→S_B`、`C_A→C_B`、`S_A→C_A`、`S_B→C_B` 可由
> `S_A, S_B, C_A, C_B` 全部同周期满足。`G` 有环只说明**该表示**不足。
>
> 正确表述：
> **若 `G` 无有向环，则"一个线性顺序 + 正反两趟"满足 `G` 的全部同周期要求；
> 反之不成立。**

**证明.** `G` 无环 ⇒ 存在拓扑序；把它作为 `L`，正向走一趟即可满足 `G` 的每条边。∎

**意义与边界**：`G` 的无环性可作为一条**配置期校验规则**（拒绝该表示覆盖不了的拓扑），
但**不等于**"拓扑不可满足"。判断一般阶段调度是否可能，必须在**实际阶段顶点**
`S_i`/`C_i` 的依赖图上查环——该检查**尚未实现**。

### 3.7 与单入口模型的对应

上游在一次遍历中用 `R` 与 `S` **同时**求一个顺序。以 Jazzy/master 的
`build_controllers_topology_info()` 为例：它把 `R` 写成 `following/preceding`，
把 `S` 也写成 `following/preceding`（方向相反）。当两条边同时存在于同一对 `(A,B)` 时，得到

- `A.following = {B}`、`A.preceding = {B}`、`B.following = {A}`、`B.preceding = {A}`

——同一个控制器同时出现在对方的**两侧**，即顺序图里出现 **2-环**；
排序启发式遇到矛盾时让**先插入者胜**，于是**静默**退化为一周期延迟。

**Humble 的情形不同，但结论相同**（§4.1 插桩实测）：它的比较器在参考边处**提前返回**，
状态边从未参与排序。因此：

| | Humble | Jazzy / master |
|---|---|---|
| 状态边是否参与排序 | **否**（被提前返回遮蔽） | 是（与参考边形成 2-环） |
| 双向边的结果 | **确定的** reference-first | **随加载顺序翻转** |
| 诊断 | 无 | 无 |

按定理 1，**两者都不是启发式写得不好，而是单入口模型下无解**：
只要每个控制器只有一个 `update()` 入口，就不存在同时满足两条边的顺序。
上游的 state chaining 与 reference chaining 各自覆盖单向场景；
**双向场景是未被覆盖的区域**。

### 3.8 最少几趟：一个平凡分类，以及它**不能**支持的主张

定理 1 只说明**一趟不够**，定理 3 只说明**两趟充分**。两者之间的空洞是：
**最少需要几趟？两趟是否最优？**
（完整证明与穷举见 `doc/PASS_LOWER_BOUND.md`。）

**结论先行（2026-09-23 修正）**：对任意无自环要求图 `D`，
`κ(D)` 就是"无边 0 / 非空无环 1 / 含环 2"——任取一个顶点全序，把边按正、反向二分即可。
所以这一节**没有**发现任何难解问题，也不能支持"最优调度"叙事；
它的唯一用途是说明"再多加几层调度也消不掉延迟"。下面的 P1–P3 保留为记录。

定义**同周期要求图** `D`：边 `u → v` 表示"`v` 必须观察 `u` **本周期**写入的值"，
于是参考边与状态边都变成 `D` 中的有向边，双向对给出 2-环。
单入口模型下，一次**趟**是节点集的一个全序，边 `u → v` 被该趟满足当且仅当 `u` 先于 `v` 被访问。

> **定理 P1（充要）.** `k` 趟调度存在 **当且仅当** `E_D` 可划分成 `k` 个**无环**子集。

**证明.** (⇐) 每个无环类取一拓扑序作一趟，该趟满足该类的全部边。(⇒) 一趟满足的边集必与
一个全序一致，故无环。∎

> **推论 P1.** 一趟可行 **当且仅当 `D` 无环**。
> **推论 P2.** 任意无环 `D` **一趟即可**，因此更不需要两趟。
> **定理 P2（下界）.** 若边集 `S` **两两不能共处一趟**，则最少趟数 `≥ |S|`。
> **推论 P3（最优性）.** 对**每一级都双向**的级联（**任意深度**），最少趟数**恰为 2**。

**推论 P3 的证明.** 每级给出一个 2-环，其两条边两两冲突 ⇒ 下界 `≥ 2`；
把边分成"全部状态边"与"全部参考边"两类，二者各自无环（树的两个定向）⇒ `≤ 2`。∎

**为什么这重要**：

1. 它把 C3 从**充分性构造**升级为**最优性定理**——
   `§3.5` 的两趟方案**在趟数意义下不可改进**；
2. 它澄清了深度与趟数的关系（本项目最易被误读之处）：

   | 量 | 随深度 `D` 的变化 |
   |---|---|
   | **最少趟数** | **恒为 2**（与 `D` 无关） |
   | **单趟滞后** | **恰为 `D`**（定理 2） |
   | 两趟滞后 | 0 |

   **"深"本身不要求更多趟；它惩罚的是坚持只用一趟。**
3. 它给"上游单向场景没问题、双向场景无解"一个精确的形式化解释：
   单向场景的 `D` 无环（推论 P1 ⇒ 一趟即可），双向场景的 `D` 含 2-环（定理 1 ⇒ 一趟无解）。
   上游的 state/reference chaining 分别对应 `D` 的一个无环子类，而双向场景需要**两个**。

**限制与更正（必须写进 threats）**：本文早期草稿称一般 `D` 的最少无环边覆盖数是 **NP-难**的，
**该说法是错的，已撤回**。对任意无自环有向图 `D`，任取一个顶点全序 `π`，把边分成
"沿 `π` 增大的边"与"沿 `π` 减小的边"，二者都不含回路，故
`κ(D) = 0`（无边）/ `1`（非空无环）/ `2`（含环），平凡可判定。
**由此推论 P3 不是树形双向级联的独立发现**，而是该分类的特例；它只能用于说明
"完整阶段遍历次数"这一维度已到底，**不能**推广成最少 CPU 时间、最小端到端延迟或任意调度最优。
另外，该"边覆盖"模型只要求"每条边曾在某一趟顺序正确"，不保证所有数值属于同一逻辑周期；
严格的充分性证明应建立在阶段顶点 `S_i`/`C_i` 的依赖图上，这一步**尚未完成**。

## 4. 上游行为的实证
### 4.1 真实 Humble 代码：确定性的 reference-first

测试 `controller_manager/test/test_upstream_ordering.cpp`（2 用例，均通过）构造一个双向对：

- parent：`command_interface_configuration()` 含 `ord_child/ref`（参考边），
  `state_interface_configuration()` 含 `ord_child/state`（状态边）；
- child：导出 `ref` reference interface，并驱动硬件命令接口 `joint2/velocity`。

| 注册顺序 | 实际执行顺序 |
|---|---|
| parent 先 | `[parent, child]` |
| child 先 | `[parent, child]` |

**两种注册顺序都得到"参考生产者在前"**，与加载顺序无关。
因此 **state 边永远是陈旧的那一条**——这是**推论 1 在真实代码上的直接验证**，
不依赖任何移植。

**机制（用插桩实测，非推理）**：我们在 `controller_sorting` 比较器入口临时插桩，
打印每次调用的 `ctrl_a`/`ctrl_b` 及其命令/状态接口列表。结果：

```text
DBG cmp a=ord_parent(state=2) b=ord_child | a.cmd=[ord_child/ref,] a.state=[ord_child/state,]
```

**每个用例中比较器只被调用一次**，说明它在**第一个检查**处即返回 `true`：
`get_following_controller_names(ord_parent)` 因 `ord_child/ref` 而包含 `ord_child`，
比较器据此直接把参考生产者排在前面，**提前返回**。

这带来一个比"静默选一条"更强的结论：Humble 的比较器末尾**确实**有一段
状态接口子句，且带着明确的未完成标记：

```cpp
// If the ctrl_a's state interface is one exported by the ctrl_b then ctrl_b should be in front
// TODO(saikishor): deal with the state interface chaining in the sorting algorithm
```

但在**双向对**上这段代码**根本不可达**——参考边的提前返回把它完全遮蔽。
换言之，Humble 的"确定 reference-first"**并不是在两条矛盾约束中做了取舍**，
而是**状态边从未参与排序**。（该子句只在"仅状态边、无参考边"的路径上才可能生效。）

### 4.2 冲突完全静默：声明状态边不被校验

`configure_controller(parent)` **成功接受**了 `ord_child/state` 这个
**没有任何控制器导出的** state 接口声明。即：

- 声明状态边在配置期**可行且不被校验**（真实校验发生在激活时 claim 租借接口的阶段）；
- 该声明**不参与排序**（比较器把它当作与参考边冲突的约束，而参考边先被检查并返回）；
- 结果：**没有报错、没有告警、没有日志提示**。

这解释了为什么该缺口长期未被发现：**拓扑声明层与调度层对同一对控制器给出互相矛盾的要求，
而两层都不检查对方。**

### 4.3 Jazzy / master：从"确定"变为"依赖加载顺序"

Jazzy 的 `controller_manager.cpp` 中 `controller_sorting` 出现 **0** 次，
而 `build_controllers_topology_info` / `update_list_with_controller_chain` 出现 **6** 次
⇒ Jazzy 已换成 master 那套递归插入启发式。把这两个函数从 Jazzy 与 master 提取、
去注释与空白后比较，**逐字节相同**：

```text
build_controllers_topology_info     jazzy_len=2566  master_len=2566  identical=True
update_list_with_controller_chain   jazzy_len=2523  master_len=2523  identical=True
```

该启发式的关键在第一行：

```cpp
if (new_ctrl_it != ordered_controllers_names_.end()) {
  return;                       // 已经在列表里 → 直接返回，后续约束被静默忽略
}
```

即：**第一次插入决定位置，之后所有冲突约束被静默丢弃。**
`research/topology_analysis/upstream_order_sim.py` 的移植执行结果：

```text
### 两个控制器，双向边，加载顺序 ['A','B']
  resulting run order   : ['A', 'B']
  edge A->B [reference] : same-cycle (fresh)
  edge B->A [state]     : ONE-CYCLE DELAY

### 两个控制器，双向边，加载顺序 ['B','A']
  resulting run order   : ['B', 'A']
  edge A->B [reference] : ONE-CYCLE DELAY
  edge B->A [state]     : same-cycle (fresh)

### 三级链 --- 加载顺序 ['r','m','l']
  edge r->m [reference] : same-cycle (fresh)
  edge m->r [state]     : ONE-CYCLE DELAY
  edge m->l [reference] : same-cycle (fresh)
  edge l->m [state]     : ONE-CYCLE DELAY
```

**三条结论：**

1. 双向边**不会报错**——它在两条矛盾约束中静默选一条；
2. 选哪一条由**控制器加载顺序**决定，**不由拓扑决定**；
3. 三级链上会出现**逐边混合**（有的边新鲜、有的陈旧），而不是一个可预测的全局延迟。
   这对**确定性**是实质性问题。

### 4.4 版本差异汇总（论文口径）

| | Humble（本地真实代码**实测**） | Jazzy / master（源码 + 逻辑移植） |
|---|---|---|
| 排序实现 | `std::stable_sort` + `controller_sorting` 比较器 | 递归插入启发式 |
| 双向边的结果 | **确定的** reference-first | **随加载顺序翻转** |
| state 方向 | 系统性陈旧 | 随加载顺序可能陈旧某一边 |
| 诊断 | 无 | 无 |

**共同点（主结论）**：单趟执行下双向耦合**必有一条边陈旧，且完全静默**。
**差异点**：从 Humble 升到 Jazzy，**同一拓扑的执行顺序会从"确定"变成"依赖加载顺序"**。

### 4.5 方法学限制

1. §4.3 是**逻辑移植 + 源码逐字节比对**，**不是运行 Jazzy 代码**；
2. 真实代码把迭代器传入递归函数，而函数内部会 `insert` 使迭代器失效；
   移植用下标建模，**可能掩盖真实行为**（这本身可能是上游的潜在缺陷）；
3. `is_interface_a_chained_interface` 只看前缀是否匹配某个控制器名，**不校验接口是否真被导出**；
4. Humble 的 chainable 控制器**不导出** state interface（那是 Jazzy+ 能力），
   因此 §4.1 只验证了**排序行为**，**无法**在 Humble 上验证"父读到陈旧状态值"的数据通路。

## 5. 两阶段契约与实现

### 5.0 设计原则：把 (SE) 换成两阶段

定理 1 说明，只要坚持 (SE)——每控制器一个融合调用点——双向同周期就无解。
因此唯一的出路是**放弃 (SE)**，把摄取与产生拆成两个调用点。但拆法有约束：

| 设计选择 | 若选错会怎样 | 本文的选择 |
|---|---|---|
| 用**两份**拓扑（摄取序 + 产生序） | 存储翻倍，且两份拓扑可能不一致 | **一份**线性化，两个方向遍历（§5.1） |
| 摄取序用逆后序 | 只要它是合法"子先于父"顺序即可 | `postorder` 正向 |
| 产生序另选一个拓扑序 | 需要第二份数组 | `postorder` **反向**——后序反转天然是"父先于子" |
| 阶段之间不做校验 | 无法发现"读到上一周期的值" | 每值带周期号与采样时间，阶段内校验（§5.2） |
| 失败时部分提交 | 硬件命令出现新旧混合 | 整组提交，失败则**任何 sink 都不调用**（§5.3） |

**第 3 行是本文的一个小而关键的观察**：后序（postorder）的反转**天然**是
"父先于子孙"的合法顺序（后序保证每个后代排在其祖先之前）。
因此**一份线性化同时满足两个方向**，不需要为命令阶段单独维护拓扑数组。
这既给出定理 3 的 `O(|V|)` 存储，也让实现与 FineMote 的"一个注册表、两个方向"完全对应。

### 5.1 执行顺序规范

```text
update stage : postorder，FORWARD   （子先于父）
reference    : 根的一次外部快照
handle stage : 同一顺序，BACKWARD   （父先于子）
validate     : 周期标识、采样年龄、有限性
commit       : 叶 scratch 拷入控制器自有的 command sink
```

### 5.2 数据契约

每个值组带 `StagedFrame`：

```cpp
struct StagedFrame {
  std::uint64_t cycle;      // 生产该值的执行组周期
  std::int64_t  sample_ns;  // 最旧输入采样时间
  bool          valid;      // 仅在本周期对应阶段成功后为真
  std::uint32_t fault_code; // 控制器自定义故障码，0 表示未上报
};
```

由执行组强制（而非靠约定）的关键约束：

- 叶节点状态阶段默认把 `sample_ns` 记为本周期；可上报更旧的真实采样时间，**但不能是未来**；
- **复合节点的 `sample_ns` 由执行组用"最旧子节点采样时间"覆盖**，节点写什么都不生效
  ⇒ **无法重新盖章伪装新鲜**；
- 节点输出的状态、reference、actuator 必须有限，否则该周期失败。

### 5.3 失败语义

- **状态阶段**任一步失败 ⇒ **命令阶段完全不进入**；
- **命令阶段**失败或写出非有限值 ⇒ 返回 `command_failed`，**任何 sink 都不会被调用**
  ⇒ 硬件命令缓冲**不会出现"部分新、部分旧"**；
- sink 在 `commit()` 中返回 false 属**硬件写入故障域**：执行组报告 `command_failed`，
  但**不承诺回滚**已提交的其它叶节点。

> **保留上一周期命令不是安全策略。** 调用方必须在看到非 `committed` 结果后执行
> 应用定义的故障动作。软件提交不等于总线原子同步，也不等于物理动作原子。

### 5.4 依赖边的来源

命令边来自**原生机制**，而不是新的 parent 字段：

- 子控制器通过 `export_reference_interfaces()` 导出 `<child>/<port>`；
- 父控制器的 `command_interface_configuration()` 里出现 `<child>/<port>`；
- 执行组在配置期按 `/` 前缀匹配成员名：前缀是成员的接口是 reference 接口，
  前缀不是成员的是普通硬件命令接口。

因此：交换控制器声明顺序**不改变**计划；一个 reference 接口有两个写者、多个根、成环、
引用不存在的成员、声明了 actuator 端口却无 sink，**均在配置期直接抛错**。

### 5.5 两种宿主

| | manager 宿主 | 库宿主 |
|---|---|---|
| 构造入口 | `StagedExecutionGroup::create(members)` | `create_library(spec)` |
| 依赖 `ControllerManager` | 是（薄适配） | **否** |
| 节点可单独加载/激活 | 是 | 否（整树在一个插件内） |
| 可与原生 chainable 混用 | 是 | 否（只 claim 硬件接口） |
| 复用内核 | **同一份** | **同一份** |

### 5.6 实时路径约束（重要工程发现）

第一版两趟实现在 `update()` 的切换路径里直接调用了加锁的成员刷新，结果**死锁**。根因：

> `ControllerManager::switch_controller()` 在**持有 `controllers_lock_`** 的同时
> 通过条件变量等待实时线程应用切换。因此**实时路径上任何获取该锁的代码都会死锁**：
> 实时线程阻塞在锁上 → 不再推进 `used_by_realtime_controllers_index_` →
> 等待切换的线程在 `wait_until_rt_not_using()` 里**永久自旋**。

修复：

- 非实时线程（`set_two_phase_execution()`）**可以**加锁刷新；
- 实时路径改为**脏标志**：切换后只置 `two_phase_entries_dirty_ = true`，
  在**下一个周期开头**用本线程已持有的 `rt_controller_list` 重建成员
  （`O(n)` `dynamic_cast`，每个切换最多一次），**全程不加锁**。

**任何接入 `ControllerManager` 实时循环的新机制都必须遵守这条约束。**

## 6. 代价量化：滞后一个周期值多少

### 6.1 为什么不能用 RMS 跟踪误差

第一版实验用"正弦参考下的 RMS 跟踪误差"作为指标，结果滞后 0→3 周期**几乎不变**
（比值 0.97–1.00）。原因是量纲没对上：1 kHz 控制下 1–3 个周期只有 1–3 ms，
对 1 Hz 参考和低带宽回路完全可以忽略。

**这是一条方法学教训**：必须选一个**能暴露效应**的指标。对"反馈用了陈旧状态"这类问题，
正确框架是**纯传输延迟**，正确指标是**相位裕度**。

### 6.2 相位裕度定律

反馈路径中 `L` 个周期的滞后等价于纯传输延迟

```text
τ = L · Δt
```

对开环 `L(s) = C(s)·P(s)·e^{−sτ}`，穿越频率 `ω_c` 处的相位裕度损失为

```text
ΔPM = ω_c · τ = 2π · f_c · L · Δt  [rad] = 360 · f_c · L · Δt  [deg]
```

注意 `ΔPM` **与 `f_c·Δt` 成正比**——即与"穿越频率占控制频率的比例"成正比。
**这解释了为什么危害是相对的。**

表 6.1：每周期代价（`Δt = 1 ms`，即 1 kHz）

| 穿越频率 `f_c` | 每周期损失 | `L=1` | `L=2` | `L=3` |
|---|---|---|---|---|
| 10 Hz | 3.6° | 3.6° | 7.2° | 10.8° |
| 50 Hz | 18° | 18° | 36° | 54° |
| 100 Hz | 36° | 36° | 72° | 108° |
| 200 Hz | 72° | 72° | 144° | 216° |

表 6.2：闭式验证（PD + 双积分器，`kp = 10, kd = 600`，`f_c ≈ 95.5 Hz`）

| `L` | `τ` | 相位裕度 |
|---|---|---|
| 0 | 0 ms | **90.0°** |
| 1 | 1 ms | **55.6°** |
| 2 | 2 ms | **21.2°** |
| 3 | 3 ms | **−13.1°（不稳定）** |

低带宽对照（`kp = 10, kd = 60`，`f_c ≈ 9.5 Hz`）：`L=0` 为 89.8°，`L=3` 仍为 **79.5°**。

### 6.3 带宽上限

给定相位裕度预算 `B`（例如 30°）：

```text
f_c ≤ B / (2π · L · Δt)
```

`Δt = 1 ms`、`B = 30°` 时：`L=1` → 83 Hz；`L=2` → **42 Hz**；`L=4` → **21 Hz**。

> **如果级联深度是 `D` 且使用单趟执行，那么为保住 30° 裕度，闭环带宽被迫压到约
> `1/(12·D·Δt)` 以下。两趟执行把这条限制去掉。**

这是一条可直接写进论文的、可操作的结论：**深度不只是"多跑几层"，它直接决定了你能做多快的控制。**

### 6.4 调度侧的闭环验证（本轮补充）

`hierarchical_control/test/test_scheduling_performance.cpp`（4 用例，全部通过）
把"调度滞后 `L`"与"可用增益上限"直接接起来：被控例 `x'' = u`，
`u = kp(r − x_delayed) − kd·v_delayed`，`kp = 100`，控制器 1 kHz，
**被控对象用精确离散化**（控制量在步内常值：`x ← x + Δt·v + Δt²/2·u`，`v ← v + Δt·u`），
因此**不存在积分误差冒充控制极限**。

表 6.3：可用增益上限

| `L` | 定律**预测** | 时间域**实测**（二分，判据峰值有界） | 相对偏差 |
|---|---|---|---|
| 0 | 无上限（>20000） | >20000（`kd=20000` 仍有界） | — |
| 1 | **1570.8** | **1582.8** | +0.8% |
| 2 | **785.3** | **856.6** | +9.1% |
| 3 | **523.5** | **591.8** | +13.1% |

预测上限由 `PM = 0` 解出；实测上限由二分搜索得到。

**两个量必须分开读**：

- **定律预测**精确满足 `(L+1)` 律：`预测(1)/预测(2) = 2.000`、`预测(1)/预测(3) = 3.001`；
- **实测**系统性**高于**预测（+1%…+13%），因为判据是**有限时域**
  （0.5 s 内峰值有界）而非无穷时域稳定性边界。因此实测比值
  `实测(1)/实测(2) = 1.848`、`实测(1)/实测(3) = 2.675`，**略低于** `(L+1)`。
  这一差距被**明确报告**，不作为噪声抹去。
- 另有 `±5%` 边界的逐点确认：`0.95×预测` 时全部有界，`1.05×预测` 时全部发散。
- **定律预测、时间域确认**：`kd = 600` 时，`τ = 0.9·τ₀` 有界、`τ = 1.3·τ₀` 发散，
  其中 `τ₀` 由 `PM = 0` 解出；
- **代价由绝对延迟决定**：同样 1 个周期，100 Hz 的裕度损失是 1 kHz 的 **10.00 倍**
  （该比值恰好为 10，与 `ΔPM ∝ Δt` 一致）；
- 另有 `kd = 600`、`L = 3`（预测裕度 −13.1°）时时间域**发散**，
  而 `L ≤ 2` 有界——定律预测的失稳起点被时间域独立确认。

**即：调度契约确实转化为控制权限。**
但须注意：这证明的是「**两趟执行下深度不惩罚控制权限**」，
**不是**「两趟执行让控制性能更好」——见 §7.4。

### 6.5 非线性稳健性（**已用正确积分重测**）

一个自然的质疑是："上述代价是不是线性模型的产物？用更真实的被控对象能否规避？"
我们在同一被控例上加入**粘性摩擦、库仑摩擦、编码器量化、执行器饱和**重测。
早期版本曾报告"摩擦与量化不改变结论（差异 < 0.1%）"，
但那个数值**建立在错误的积分格式上**（§7.4.4），因此本轮用
`x''=u` 的精确逐步更新重做，并**先校验积分格式本身**（其给出的上限须与相位裕度定律吻合）。

**校验**（`L=1,2,3` 的真实可用增益上限）：

| `L` | 相位裕度定律预测 | 积分实测 | 偏差 |
|---|---|---|---|
| 1 | 1570.8 | 1582.8 | +0.8% |
| 2 | 785.3 | 856.6 | +9.1% |
| 3 | 523.5 | 591.8 | +13.1% |

实测**系统性略高于**预测，因为判据是**有限时域**（0.5 s 内峰值有界），
比无穷时域的稳定性边界更宽松。这一差异被**明确报告**而不是抹平。

**结论一：摩擦只在"远小于控制权限"时才不改变结论。** 取参考幅值 1、`kp = 100`，
比例控制权限约 `kp·A = 100`，`L = 1`：

| 库仑摩擦 `f_c` | `f_c`/权限 | 上限相对无摩擦 |
|---|---|---|
| 0.2 | 0.002 | **+0.05%** |
| 2.0 | 0.02 | **+0.42%** |
| 20.0 | 0.2 | **+10.9%** |
| ≥200 | ≥2.0 | 无上限 |

**正确表述**：`f_c ≲ 2%·kp·A` 时上限变化 < 0.5%，成本是**延迟驱动**的；
一旦摩擦与控制权限**可比**（`f_c ≈ 20%·kp·A`），上限已被抬高 10.9%，**模型开始起作用**。
早期"差异 < 0.1%"之所以成立，是因为当时 `f_c = 0.2` 而控制力约 `kd·v ≈ 10⁴`——
摩擦小 5 个数量级，**该比较本身是空洞的**。因此我们**不**声称无边界的稳健性，
而是给出**边界位置**。

**结论二：量化确实不改变上限**，在分辨率粗到参考幅值的 10% 时峰值仍一致。

**结论三：饱和掩盖失稳而不消除它。** `kp=100`、`L=2`（`τ=2 ms`）、
`t=1 s` 注入 `+0.05` 速度扰动：

| `kd` | 线性预测相位裕度 | 线性（无饱和） | 饱和 `u_max=200` | 饱和后跟踪误差 RMS |
|---|---|---|---|---|
| 300 | +51.5° | 有界（峰值 0.098） | 有界（峰值 0.098） | 0.715 |
| 600 | +21.2° | 有界（峰值 0.051） | 有界（峰值 0.051） | 0.713 |
| 1000 | **−24.6°** | **发散** | **有界（峰值 0.031）** | **0.711** |
| 2000 | **−139.2°** | **发散** | **有界（峰值 0.016）** | **0.709** |

`kd = 1000` 时线性回路发散，饱和回路峰值仅 0.031——**看起来稳定**。
但其**跟踪误差 RMS = 0.711**，而 ±1 参考自身的 RMS 是 `1/√2 = 0.707`，
即**输出与指令基本无关**，回路并未在控制。

> **"它不炸了"不等于"它能工作"。** 这是单趟 + 深级联在实际机器人上最危险的失效形态：
> 故障被饱和掩盖，只表现为精度差、抖动或执行器持续饱和。
>
> 附注：`kd = 300`（裕度 +51.5°）的**健康**回路 RMS 也是 0.715——
> 在**该被控对象**上 RMS 本身无法区分好坏。因此判据必须是**相位裕度 + 幅值**，
> 这也再次印证 §6.1 的指标教训。

**本节结论**：深度代价是**结构性的**（在摩擦远小于控制权限的区间内与模型无关）；
但该区间**有边界**，越界后模型开始起作用；饱和只改变**表现**（发散 → 有界），
不恢复控制能力。因此在带饱和的系统上做实验**必须同时报告相位裕度与跟踪误差**。

## 7. 实验

### 7.1 公平对照（同一算法、同一状态快照、同一频率、同一故障语义）

三种实现：原生 chaining（3 个 chainable 控制器）、手写 composite（1 个插件，内部两阶段）、
阶段化执行组（3 个控制器 + `StagedExecutionGroup`）。

| 观测 | 原生 chaining | 阶段化执行组 |
|---|---|---|
| 每周期叶命令 | 三种实现**逐位相等**，且等于解析值 | 同左 |
| `leaf_a` 命令阶段失败一周期 | 失败叶保持旧值 | 失败叶保持旧值 |
| **健康兄弟 `leaf_b`** | **写入新值** | **保持上一周期值** |
| 两兄弟是否一致 | **否（一新一旧）** | **是（都保持旧值）** |
| 下一周期恢复 | 正确 | 正确 |

这正是 POV 底盘要避免的"部分新、部分旧"情形。

### 7.2 真实 `ControllerManager`

级联 `root → mid → leaf`，每级估计**不可被父重推导**（对自己子估计的一阶滤波），
在第 10 周期注入叶输入阶跃：

| 模式 | leaf lag | mid lag | root lag |
|---|---|---|---|
| 单趟（原生 `update()`，列表正向） | 0 | **1** | **2** |
| **两趟（opt-in）** | 0 | **0** | **0** |

即：**真实管理器里，单趟执行下根节点的信息陈旧整整一个"深度"（这里 2 个周期）；
两趟执行下所有层级都是同周期。**

### 7.3 真实 Gazebo 闭环

平台：Ubuntu 22.04 + Gazebo Classic 11.10.2 + ROS 2 Humble + `gazebo_ros2_control`。
两轮差速底盘，三个自研控制器（`wheel_left`/`wheel_right` 为叶，`chassis` 为根），
`chassis` 与每个轮之间**同时存在两条边**。

测量方式（**与理论无关、不依赖真值**）：`chassis` 发布它**本周期用到的**轮行程，
每个轮发布它**自己的**轮行程；测量节点把两条时间序列做**整数周期对齐**，取使误差最小的位移量。

表 7.1：状态边陈旧量

| 模式 | 控制率 | 左轮行程滞后 | 右轮行程滞后 | 墙钟代价 |
|---|---|---|---|---|
| 单趟 | 50 Hz | **1 周期** | **1 周期** | 20 ms |
| 两趟 | 50 Hz | **0 周期** | **0 周期** | 0 ms |
| 单趟 | 20 Hz | **1 周期** | **1 周期** | **50 ms** |
| 两趟 | 20 Hz | **0 周期** | **0 周期** | 0 ms |

**滞后恒为"一个周期"，与控制率无关；但它的墙钟代价随周期线性增长（20 ms → 50 ms）。**
这正是 `ΔPM = ω_c·L·Δt` 的输入项：**同样的契约违反，控制率越低，代价越大。**

### 7.4 代价与负结果（**必须同章报告**）

#### 7.4.1 不更快

| 运行 | 方案 | min | median | max |
|---|---|---|---|---|
| 1 | 原生 chaining | 1.42 | 1.87 | 39.5 |
| 1 | 手写 composite | 0.40 | 0.65 | 8.5 |
| 1 | 阶段化执行组 | 3.21 | 4.28 | 114.2 |

（单位 µs；200 周期；RelWithDebInfo；非实时虚机）
**阶段化执行组的中位耗时约为手写 composite 的 2 倍。**

结构性原因：两趟每周期多付**一次额外列表遍历** + **每控制器一次额外虚调用**
（`update_phase` + `handle_phase` vs 一次 `update`）+ **每控制器每阶段一次帧校验**；
而手写 composite 是**一个插件、一次内联调用**，虚调用被编译器消掉。

**口径**：测的是 **CPU 时间**，而 FineMote 主张的是**控制延迟**——两者不是同一个量。
用 CPU 时间否定控制延迟主张是**指标错配**。

其他限制：`max` 波动 8–300 µs（调度噪声），**不能**当 deadline miss 统计；
未报 p95/p99；未做 CPU 绑定；未做消融。

#### 7.4.2 跟踪误差无收益

Gazebo 底盘外环 `f_c ≈ 0.5 Hz`、`Δt = 20 ms`：

```text
ΔPM = 360 × 0.5 × 1 × 0.02 ≈ 3.6°
```

**一个周期只损失 3.6°**，在该被控对象上任何测量都看不出差别。
这不是机制无效，而是**该被控对象不在机制起作用的区间内**。

本轮进一步发现一个更精确的方法学结论：
**能用跟踪误差看到收益的场景，与滞后造成危害的场景，不是同一个场景。**
在 §6.4 的高带宽被控例上，小信号跟踪误差 RMS **无法区分**调度：

- 双积分器 + PD **无积分作用** ⇒ 对位置参考的直流增益不为 1，
  稳态位置幅值远小于参考幅值，误差 RMS 被参考自身 RMS 主导（≈ `1/√2`），与滞后几乎无关；
- 加入积分作用后环路阶数升高，误差 RMS 仍由参考主导。

| 敏感指标 | 不敏感指标 |
|---|---|
| 相位裕度、可用增益上限、失稳点 | 小信号跟踪误差 RMS |
| 阶跃响应的初始滞后周期数 | 低频正弦的 RMS 误差 |

#### 7.4.3 省集成代码不独有

通用 composite 库以同样的数据驱动方式做到"加一个节点 = 一条配置"，
**且不需要修改 `ControllerManager`**，复用**同一份内核**。
因此"减少手写集成代码"**不足以**支撑修改上游管理器；
交付形态应为「**独立 header-only 库 + 可选薄适配**」。

#### 7.4.4 一个被误读为收益证据的数值伪影（方法学修正）

早期代价量化报告了"可用增益预算随深度按 `1/(L+1)` 缩水"，
实测比值 `1 : 0.502 : 0.311 : 0.225`，看似与理论吻合。**这是错误的。**

**根因**：`test_stale_state_cost.cpp` 的 `simulate_plant()` 使用**显式 Euler**：

```cpp
const double next_velocity = velocity + dt * (command - plant.viscous * velocity - friction);
```

`command` 含 `−kd·history_velocity[index]`，于是

```text
v ← v + Δt·(−kd·v + …)  =  (1 − Δt·kd)·v + …
```

放大因子 `|1 − Δt·kd|` 在 `Δt·kd > 2` 时大于 1 ⇒ **积分格式自身发散**。
由于该格式中的有效阻尼就是 `kd`，这个阈值**随深度按 `1/(L+1)` 缩放**，
**精确复现了那组比值**——它与调度无关。

**修正后的真实上限**（§6.4，精确离散化）：

| | 显式 Euler "上限" | 精确离散化的真实上限 |
|---|---|---|
| 定律 | `Δt·kd = 2` ⇒ `1/(L+1)` | `PM = 0` |
| `L=0` | ~2000 | **无上限**（`kd = 20000` 仍有界） |
| `L=1` | ~1000 | **1570.8** |
| `L=2` | ~667 | **785.3** |
| `L=3` | ~500 | **523.5** |

两者数值接近（这正是此前未被发现的原因），但**属于完全不同的量**。
**教训**：**代价量化必须核查积分格式**，否则会把求解器极限报告为控制极限。

### 7.5 复杂度与实时性

**计划生成（非实时路径）。** 配置期完成拓扑解析、字符串处理与存储分配。
一次性的工作量是 `O(|V| + |E|)`，与控制器数量线性相关；
`V` 为控制器数、`E` 为参考边数。此阶段允许分配、允许抛异常。

**运行路径。** 每周期只做指针索引，**不含**查找、构图、字符串比较或分配：

| 操作 | 每周期次数 |
|---|---|
| 两次列表遍历（状态阶段反向、命令阶段正向） | 各 `O(|V|)` |
| 每控制器每阶段一次虚调用 | `2|V|` |
| 每值帧校验（周期号、采样年龄、有限性） | `O(|V| + |E|)` |
| `commit`：叶 scratch → 控制器自有 sink | `O(叶数)` |

**零分配是实测的，且范围被严格限定。** 我们覆盖全局 `operator new/delete` 计数：
`StagedExecutionGroup::run()` 自身在配置完成后 **100 次调用 0 次分配**（已断言）。

> **但 `ControllerManager::update()` 整体仍会分配**，来源是 Humble 既有代码：
> `rt_controller_list` 的 `for` 循环**按值复制** `ControllerSpec`（含字符串与 vector），
> 以及 `is_controller_active()` 最终调用的 `LifecycleNode::get_current_state()`
> 在 `MutexMap::add()` 中分配。
> 因此正确表述是「**本方案没有新增实时路径分配**」，
> **不是**「接入后 `update()` 变成零分配」。

**实时安全的硬约束（本项目的工程发现）。** 实时路径**禁止获取 `controllers_lock_`**：
`switch_controller()` 在**持有该锁**的同时通过条件变量等待实时线程应用切换，
因此实时线程一旦抢锁就会阻塞，不再推进 `used_by_realtime_controllers_index_`，
等待线程在 `wait_until_rt_not_using()` 里**永久自旋**。
我们第一版实现正因此死锁。修复方式是：非实时线程可加锁刷新；
实时路径只用**脏标志**，在下一周期开头用本线程已持有的列表重建成员
（`O(n)` `dynamic_cast`，每个切换最多一次），**全程不加锁**。
任何接入 `ControllerManager` 实时循环的新机制都必须遵守该约束。

**耗时的量级。** 相对手写 composite，本方案中位耗时约为其 **2 倍**（§7.4.1）。
这一开销是**结构性**的（每周期多一次遍历、每控制器多一次虚调用、每阶段一次帧校验），
不是实现质量问题。

**未验证。** 我们**没有**测量 WCET、deadline miss、p95/p99，
也**没有**在实时内核上运行。所有耗时数字来自非实时虚拟机，**不能**作为实时性结论。

## 8. 方法学：我们踩过的坑

审稿人必然会问"为什么第一版看不出差别"，因此本章是**必需**的。

1. **子状态必须不可被父廉价重推导。**
   第一版叶节点状态是 `travel += ∫v·r dt`，父节点完全可以自己读 `wheel/position`
   再乘半径得到同样的值 ⇒ **不构成依赖**，案例研究因此看起来"机制没用"。
   修正：叶节点加入**滤波器内部状态**（`filtered_velocity_ = α·filtered_velocity_ + (1−α)·v`，
   `α = 0.85`），积分的是**滤波后**的速度；该状态依赖控制器自己的历史，
   父节点**无法**从瞬时关节位置重建。这才是一个真实的"叶端估计器"。
   **推广**：父能用输入和已知几何重算的量，**不构成依赖**。
2. **评估指标必须对纯延迟敏感。** 见 §6.1 与 §7.4.2。
3. **饱和会掩盖不稳定。** 带饱和的系统必须**同时报告跟踪误差**，
   否则"没炸"会被误读成"能用"。
4. **数值积分格式会冒充控制结论。** 见 §7.4.4。
5. **因果对齐要用整数周期对齐**，不要用浮点时间戳（时间戳抖动会污染结果）。
   案例研究用的是"底盘用掉的行程"vs"轮子当时拥有的行程"的整数周期交叉对齐。
6. **一个线性顺序就够。** 不要维护两份拓扑数组；后序的反转就是合法的父先顺序。
7. **测量脚本必须检查被测量命令的退出状态。**
   在测量元编程的编译期成本时，我们第一版用**手写的 ROS include 路径**编译真实翻译单元，
   得到 0.14 s 这种"好得不像真的"数字。真相是**编译其实失败了**
   （缺 `hardware_interface`、`rcl_lifecycle`），而管道把**非零退出码吞掉**，
   于是"编译失败"被读成"编译极快"。改用构建系统真实解析出的 include 路径后才复现出 ~10 s。
   **这与陷阱 4 同源：工具的问题被当成了被测对象的性质。**
8. **模板错误的定位成本被低估了（一次被实践推翻的判断）。**
   我们曾评估"把节点名带进 `static_assert` 诊断"收益有限而主动放弃。
   随后在本项目自身的开发中，一个嵌套模板的编译失败反复指向
   "绑定的 `next_type` 是 `void`"，而真实原因是**测试夹具里的一条契约声明不当**
   （一个只含单个节点的绑定复用了含跨节点依赖的契约）。
   该排查花了远超预期的时间，**说明诊断可读性在嵌套模板下的价值被低估**。
   我们如实记录这一判断失误，并把"诊断携带可读节点名"列为后续工作。

## 9. 结论

### 9.1 结论

在单入口控制器模型下，同一对父子之间的**双向同周期数据流不可满足**（定理 1）；
参考一致的单趟调度使**每条状态边**结构性陈旧（推论 1），陈旧量**恰好等于级联深度**（定理 2）。
「一个线性顺序 + 两个相反遍历方向」的两阶段契约是**充分的**，
只需 `O(|V|)` 存储、**不需要第二份拓扑顺序**（定理 3），并可在配置期判定环形依赖（推论 2）。

该契约的控制代价可用经典框架精确量化：`L` 个周期 = 纯传输延迟 `L·Δt`，
相位裕度损失 `ω_c·L·Δt`，带宽上限 `f_c ≤ B/(2π·L·Δt)`（§6.2–6.3）。
本轮闭环实验在**调度侧**验证了这条链（§6.4），并**修正了一处数值伪影**（§7.4.4）。

契约在三类真实系统上成立：内核级穷举、**真实 `ControllerManager`**（单趟 2 周期 → 两趟 0）、
**真实 Gazebo 闭环**（单趟 1 周期 / 20–50 ms → 两趟 0）。

上游在双向场景下**不报错、不告警、静默降级**；在 Jazzy/master 上还**依赖加载顺序**。
按定理 1，这**不是启发式实现不佳，而是单入口模型下无解**。

**本文不声称性能收益。**

### 9.1.1 本文的独特性（与相邻主张的边界）

一篇以不可能性为主张的论文，其价值取决于**主张的边界是否锋利**。本文的独特性可精确表述为：

> **在"每控制器一个融合调用点"(SE) 这一模型下，双向同周期数据流不可满足；
> 且把 (SE) 换成两阶段后，**两趟就是最少趟数**。**

三点合起来构成一个**紧的**结论：**下界（不可满足）与上界（两趟且最优）相接**。具体地：

| 常见相邻主张 | 本文是否主张 | 说明 |
|---|---|---|
| 首次提出两阶段/层次化调度 | **否** | FineMote、Orocos 等已有 |
| 首次用接口连接生成状态依赖 | **否** | 上游已有（§2.2） |
| 上游存在 bug | **否** | 只能说"未被覆盖"（§2.3） |
| 我们的方案更快 | **否** | 实测约为手写 composite 的 2 倍（§7.4.1） |
| 使用位置/速度接口的级联控制 | **否** | 经典控制 |
| **双向同周期在单入口模型下不可满足** | **是** | 定理 1，含穷举验证 |
| **单趟滞后下界 = 级联深度** | **是** | 定理 2，含上界构造 |
| **最少趟数 = 要求图的无环边覆盖数；双向级联恰为 2** | **是** | 定理 P1–P2、推论 P3 |
| **滞后代价 → 带宽上限，并在真实系统验证契约** | **是** | §6、§7.2–7.3 |

**为什么这不是"显然"的**：上游分别实现了两个方向的机制，两者**各自都对**；
不可能性只在**它们同时出现**时才显现，而且上游**不报错**——
一个不报错的失效模式很容易长期不被发现（§4.2 给出它为什么静默的代码级解释）。
此外，把"两趟"从**充分**升级为**最优**需要引入趟数这一资源维度并证明下界（§3.8），
这一步与"实现一个两阶段调度器"是不同的工作。

### 9.3 元编程：把契约前移到编译期（概述，全文见附录 E）

单入口模型的不可能性是**语义层**的结论；随之而来的问题是"能否把契约**前移**，
使不可满足的拓扑在更早的阶段就被拒绝"。我们把三层契约前移到**编译期**：

| 层 | 保证 |
|---|---|
| 拓扑无环 | 含环层级**编译期拒绝**（命题 M1，强化 §3.6 推论 2） |
| 接口量纲 | 量纲作为类型（真代数），**量纲错接编译期拒绝** |
| 端口所有权 | 端口名 `"<owner>/<local>"` 的 owner 必须**存在于拓扑中** |

并让**一份编译期定义同时驱动**编译期检查与运行期计划，最终经
`create_library_group` 产出**真实可运行的执行组**（端到端测试中 `run_ns` 返回
`StagedStatus::committed`）。

**其边界必须在正文点名**（否则容易被读成"任意拓扑都被静态保证"）：

- 只覆盖**静态声明**的拓扑；YAML / `pluginlib` 动态拓扑**不覆盖**；
- 所有权检查只验证 owner **是否存在**，**不验证** owner 是否**真的导出**该端口；
- **状态端口的语义区分未下探到类型层**；
- 不检查**单位**（米/毫米量纲相同）。

因此其定位是「**编译期能力 + 运行期回退**」，**不是**取代运行期校验。
附录 E 给出完整设计、证明、负例语料与编译期成本实测。

## 附录 E：元编程——把契约前移到编译期（全文）

### E.1 机制与命题

FineMote 的机制里，顺序与层级由**类型系统与构造顺序**承载；而本项目的内核原本是
**运行期**构造（`Spec` / `parents` / `StagedGroupMember`）。本节把可判定性前移。
原型与完整论证见 `doc/METAPROGRAMMING_CONTRACT.md`。

**已实现的机制**：层级表示为类型链 `Node<Name, Parent>`（`Parent = void` 为根），
每个节点类型在编译期暴露自己的根到自身 `ancestry`。`Descendant<Name, Parent>` 在
`Name` 已出现于父的 `ancestry` 时**编译期拒绝**：

> **命题 M1.** 若 `Descendant<NameT, Parent>` 通过编译，则 `NameT` 不出现在 `Parent` 的
> `ancestry` 中；因此通过编译的层级其构造图**无环**。

由于节点的 `ancestry` 必含自身名字，该检查同时覆盖**自环**与
**任意长度的祖先复用**（即闭任意长度 ≥ 2 的环）。
这把 §3.6 推论 2 从"配置期检查后拒绝"强化为"**含环拓扑无法通过编译**"。

**必须精确区分的一点**：这**不是**"循环不可表达"。2-环是**可以写出的类型表达式**
（`Descendant<A, Descendant<B, Root<A>>>`），只是被 `static_assert` **拒绝**。
结论相同，但论证方式不同，**论文按"编译期拒绝"写，不写"不可表达"**。
（这解决了我在骨架里标注的"待严格论证"那一点。）

**实测**（`test_static_topology.cpp` 5 用例 + 编译语料 4 文件，全部通过）：自环、
2-环、3-环均被拒绝，且诊断明确指向 CYCLE；语料含一个**必须编译通过**的对照文件，
使该检查**可证伪**（否则"全部拒绝"会伪装成通过）。

**覆盖面边界（关键，且已写成测试）**：该保证只涉及**构造（树/参考）图**。
**非祖先的状态边**——例如共享子节点被另一个父消费——在这个表示里**根本无法表达**，
故编译期对它**无话可说**，**仍必须由运行期校验负责**。
因此定位是"**编译期能力 + 运行期回退**"，**不是取代运行期校验**。
另：拓扑常来自 YAML 且插件经 `pluginlib` 动态加载，这类拓扑**不覆盖**。

**编译期成本**（header-only 包必须报告，多形状实测见 `doc/COMPILE_COST.md`）：
头文件固定成本 **0.22–0.25 s**；**宽扇出每子节点 1.28 ms 且与宽度无关**；
**深链每节点随深度增长**（深度 8/16/32/64 → **3.35 / 4.07 / 5.89 / 9.63 ms**）。
在真实 `controller_interface` 翻译单元（~10 s）中增量**不超过约 5%，且落在噪声带内**。
**报告口径**：先前"9 ms/节点"是深度 64 链上的数字，**不是通用常数**，已更正；
观测增长慢于严格 `O(d²)`，故只声称"随深度单调增长"。

**维度检查（同日追加）**：`dimensional_interfaces.hpp` 把物理量纲放进接口类型，
使参考边/状态边的**量纲错接在编译期被拒绝**。量纲是**真代数**（指数向量），
故能区分**力矩 vs 能量**（力矩带角度指数 `[N·m/rad]`）、**角度 vs 位置**这类
"物理上合理但错误"的接线；上游接口是**字符串名**，**没有**这层保护。
**边界**：它检查"**声明之间的量纲一致性**"，**不是**本项目实测的
"声明了没人导出的接口"（后者仍需运行期），**也不检查单位**（米/毫米量纲相同）。
详见 `doc/DIMENSIONAL_INTERFACES.md`。

**拓扑契约接合（同日追加）**：`topology_contract.hpp` 让**一份**编译期定义同时驱动
编译期检查与运行期计划（`names`/`instances`/`parents`，根在前），
并强制**端口名必须是 `<owner>/<local>` 且 owner 必须存在于拓扑中**——
这把本项目实测的"声明了没人导出的接口"缺陷向上游的静默行为收敛了一步。
计划的不变式（长度/唯一性/单根/父存在/非自父）可在**进入内核之前**复核，
且该复核**非空洞**（7 种畸形输入全被拒）。详见 `doc/TOPOLOGY_CONTRACT_JOIN.md`。

**接合到内核（同日再追加）**：`topology_binding.hpp` 提供
`create_library_group(binding)`，直接把编译期绑定变成**可运行的** `StagedExecutionGroup`。
全链路为「一份编译期定义 → 三层检查（无环/量纲/所有权）→ 计划 → `void*` 适配 →
真实执行组」。测试**真实构造执行组并跑一个周期**（`StagedStatus::committed`，
三个成员两阶段各调用恰好一次），以覆盖"适配后的计划通过自身检查却被内核拒绝"这一失效模式。

**量纲接入端口声明（同日再追加）**：`typed_ports.hpp` 让端口**只声明一次**（作为类型），
内核所需的字符串列表与 `Contract` 均**由它生成**，因此不存在"同一事实两处声明漂移"的可能。
父子端口的**名字、顺序、量纲**一致性可**编译期**检查，其中量纲检查是
**内核（只比字符串）做不到的**；mixin 控制器**真的能在执行组里运行**
（端到端 `StagedStatus::committed`）。详见 `doc/PORT_DIMENSIONS.md`。

**未完成**：状态端口的语义区分未下探到类型层；
且所有权检查只验证 owner **是否存在**，**不验证** owner 是否**真的导出**该端口（后者仍需运行期）。

> **论文口径**：这是**已实现并测试的原型** + **已明确界定的负空间**，
> 不是"已实现编译期校验所有拓扑"，也不是"取代运行期校验"。
